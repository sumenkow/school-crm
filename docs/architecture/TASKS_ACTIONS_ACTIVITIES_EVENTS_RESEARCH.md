## 1. Исполнительное резюме и ключевое архитектурное решение

### 1.1. Контекст и предпосылки исследования
Smart Academy CRM представляет собой комплексную систему управления языковыми и технологическими курсами (Next.js 15 App Router, React 19, Supabase PostgreSQL, Tailwind CSS). По мере расширения функционала (модули «Мой день / Cockpit», воронка лидов, европейские инвойсы, учет посещаемости уроков, журнал безопасности `audit_events`, учет оттока учеников) система столкнулась с классической болезнью роста: **семантическим смешением понятий «Поручение» (Task), «Следующий шаг» (Action), «Факт взаимодействия» (Activity), «Бизнес-событие» (Event) и «Технический лог» (Audit Log)**.

В текущей кодовой базе одна и та же бизнес-ситуация (например, просроченный счет на 270 € или новый входящий лид):
- Одновременно генерирует до 4 конкурирующих карточек в разных модулях интерфейса («Мой день», карточка лида, доска `/tasks`, таблица финансов);
- Рассинхронизирует состояние между базой Supabase и `localStorage` браузера;
- Теряет результаты выполнения задач при смене устройства из-за отсутствия необходимых колонок в PostgreSQL;
- Блокирует доступ преподавателей к поручениям на уровне Row-Level Security (RLS).

### 1.2. Ключевое архитектурное решение: Модель B+ (Decoupled Model B+)
В качестве безальтернативного целевого стандарта утверждается **Decoupled Model B+**:
- **Поручения (Tasks):** Директивные сущности взаимодействия между людьми (`owner` $\leftrightarrow$ `admin` $\leftrightarrow$ `teacher`) с явным исполнителем, дедлайном, статусом приемки и обязательным результатом закрытия. Персистентно хранятся в нормализованной таблице `public.tasks`.
- **Факты работы и контакты (Activities):** Неизменяемые исторические факты совершившихся действий (состоявшийся звонок, отправленное сообщение, проведенный пробный урок, принятый платеж). Персистентно фиксируются в `public.interactions` (рефакторинг в `activity_records`).
- **Следующие шаги дня (Actions):** Операционные единицы работы, определяющие, что сотруднику нужно сделать прямо сейчас. **СТРОГО ВЫЧИСЛЯЕМАЯ ПРОЕКЦИЯ (Computed SSOT Projection)** из состояния базовых доменных объектов (`leads`, `lessons`, `invoices`, `tasks`). Создание отдельной физической таблицы `actions` в PostgreSQL **КАТЕГОРИЧЕСКИ ОТВЕРГНУТО** во избежание «чумы задач-призраков» (Ghost Task Plague) и рассогласования данных.
- **Технический аудит (Audit Logs):** Физически неизменяемый (append-only) журнал безопасности `public.audit_events`, отделенный от клиентской хроники общения и защищенный триггерами базы данных.

### 1.3. Принципы целостности (Integrity & Architectural Laws)
1. **Закон нулевых фантомных сущностей (Zero Ghost Entities):** Все сущности, влияющие на операционную деятельность (инвойсы, уведомления, причины оттока), обязаны иметь свои физические таблицы в Supabase с включенным RLS. Хранение критических данных исключительно в `localStorage` признано критической уязвимостью P1 и подлежит плановой миграции.
2. **Закон единственной рабочей единицы (Entity-Keyed Primary Work Unit):** Каждая бизнес-ситуация обязана формировать ровно одну первичную карточку действия в интерфейсе «Мой день», адресуемую по каноническому URI доменного объекта (`urn:school:invoice:<id>`).
3. **Закон замкнутой петли завершения (Completion-to-Next Loop):** Ни одно действие по лиду или ученику не может завершиться переходом в пустоту — система обязана требовать фиксации результата и назначения следующего шага.

#### Поток данных при закрытии задачи:
1. Пользователь отмечает чекбокс в `AdminDashboardView.tsx` или `/tasks`.
2. Вызывается `updateUnifiedTaskStatus(id, 'done', { comment, performerName })`.
3. В локальном хранилище сохраняются `completedAt`, `completedBy`, `result`.
4. В Supabase отправляется запрос `UPDATE tasks SET status = 'done', updated_at = now()`. Поля `result` и `completed_by` отбрасываются базой данных.
5. В таблицу `interactions` записывается текстовая строка: `«Задача закрыта: ... Результат: ...»`.
6. Генерируется локальное событие `crm-notifications-changed`.

### 3.1. 5 фундаментальных семантических измерений
Анализ выявил, что смешение понятий приводит к деградации систем. Мировые стандарты строго разграничивают 5 измерений:

```
                      СЕМАНТИЧЕСКИЙ ВЕКТОР ВРЕМЕНИ
                      
    Прошлое (t <= t_0)               Настоящее (t = t_0)             Будущее (t > t_0)
┌─────────────────────────┐     ┌─────────────────────────┐     ┌─────────────────────────┐
│   ACTIVITY / EVENT      │     │  NEXT ACTION / COCKPIT  │     │      TASK / TO-DO       │
│  (Неизменяемый факт)    │     │  (Вычисляемый шаг дня)  │     │ (Обязательство человека)│
│                         │     │                         │     │                         │
│ • Состоявшийся звонок   │     │ • «Позвонить новому»    │     │ • Поручение директору   │
│ • Проведенный урок      │     │ • «Выставить счет»      │     │ • Проверить договор     │
│ • Принятая оплата       │     │ • «Запросить отзыв»     │     │ • Подготовить методику  │
│                         │     │                         │     │                         │
│ Хранилище: Immutable DB │     │ Хранилище: SSOT Engine  │     │ Хранилище: Mutable DB   │
└─────────────────────────┘     └─────────────────────────┘     └─────────────────────────┘
             │                                                               │
             ▼                                                               ▼
┌─────────────────────────┐                                     ┌─────────────────────────┐
│   ACTIVITY HISTORY      │                                     │  TECHNICAL AUDIT LOG    │
│  (Клиентская хроника)   │                                     │  (Журнал безопасности)  │
│ Сквозная бизнес-история │                                     │ Low-level JSON diffs    │
│ для операторов и CRM    │                                     │ для DevOps и комплаенса │
└─────────────────────────┘                                     └─────────────────────────┘
```

1. **Task / To-do (Обязательство):** Будущее время ($t > t_0$). Назначено на конкретного исполнителя, имеет дедлайн, мутабельный жизненный цикл (`Open` $\rightarrow$ `In Progress` $\rightarrow$ `Completed`), статус приемки.
2. **Activity / Completed Work (Факт):** Прошлое время ($t \le t_0$). Неизменяемая запись о том, что реально произошло. Имеет точный таймстемп, автора, длительность, результат и вложения. Не может быть «отменена» — только скорректирована компенсирующей записью.
3. **Next Action / Suggestion (Следующий шаг):** Настоящее время ($t = t_0$). Контекстная рекомендация или обязательный шаг бизнес-процесса, вытекающий из состояния объекта. Не требует хранения в БД до момента фиксации факта или откладывания.
4. **Activity History (Хроника клиента):** Человекочитаемая агрегация активностей и ключевых бизнес-вех, оптимизированная для быстрого понимания контекста администратором или преподавателем.
5. **Technical Audit Log (Аудит безопасности):** Низкоуровневый, защищенный от модификации журнал мутаций строк базы данных (`INSERT`, `UPDATE`, `DELETE`), хранящий diff полей, IP-адреса, идентификаторы сессий и акторов.

### 3.2. Архитектурные паттерны ведущих платформ
- **Salesforce:** Разделение на `Task` (действие) и `Event` (событие календаря с длительностью). Синтетические read-only связи `OpenActivities` (открытые дела) и `ActivityHistory` (закрытые дела). Полиморфные связи через `WhoId` (люди: Lead, Contact) и `WhatId` (контекст: Account, Opportunity).
- **HubSpot:** Семейство объектов CRM Engagements (`tasks`, `calls`, `emails`, `meetings`, `notes`). Строгий граф ассоциаций (`crm/v3/associations`). Завершение звонка порождает объект `call`, а связанный `task` просто меняет статус.
- **Pipedrive (Activity-Based Selling):** Закон **Next Activity Invariant**: каждая открытая сделка обязана иметь ровно одно запланированное действие. Цветовая индикация в пайплайне: красный (просрочено), зеленый (сегодня), желтый (НЕТ ДЕЙСТВИЯ — тревога!), серый (будущее). Паттерн **Completion-to-Next Loop**: при закрытии действия модальное окно требует зафиксировать результат и сразу создать следующий шаг.
- **Zoho CRM:** Движок **Blueprint** (конечный автомат). Переходы между стадиями оформляются кнопками с правилами *Before* (права доступа), *During* (обязательные поля и чек-листы), *After* (автоматические триггеры).
- **Microsoft Dynamics 365:** Наследование таблиц от базовой `ActivityPointer` (`activitypointer`), полиморфный внешний ключ `RegardingObjectId`. Контрол `Timeline Wall` объединяет активности, заметки и посты.
- **Asana:** Разделение пользовательских комментариев (`comment_added`, мутабельны) и системных историй (`system stories`, неизменяемы).
- **Monday.com:** Физическое разделение обсуждений (`updates`) и GraphQL-аудита мутаций колонок (`activity_logs`).

### 3.4. Топ-7 антипаттернов глобальных CRM, выявленных при исследовании
1. **The Ghost Task Plague (Чума задач-призраков):** Преждевременное создание в базе данных тысяч автоматических задач на будущее. Если клиент оплачивает счет раньше, предварительно созданные задачи остаются висеть и требуют сложных каскадных чисток.
2. **Timeline Pollution (Загрязнение таймлайна):** Запись низкоуровневых мутаций БД (`UPDATE students SET updated_at=...`) в клиентскую ленту общения, из-за чего теряются важные звонки и комментарии.
3. **The Disconnected Note (Бесструктурная заметка):** Сохранение критических событий (отказ от учебы, причина оттока) в виде свободного текста комментария вместо типизированного события с кодом причины.
4. **The Ownerless Task (Бесхозная задача):** Существование задач без назначенного человека или роли, что приводит к диффузии ответственности.
5. **The Unclosable Loop (Разомкнутая петля):** Возможность закрыть задачу без предложения назначить следующий шаг, из-за чего клиенты «зависают» в воронке.
6. **Polymorphic Foreign Key Chaos:** Запись строковых идентификаторов без типа сущности, приводящая к нарушению ссылочной целостности в PostgreSQL.
7. **Infinite Automation Ping-Pong:** Циклические триггеры, когда закрытие одной задачи автоматически создает другую, вызывая бесконечный шторм уведомлений.

### 4.2. Природа «Action»: Физическая таблица БД против Computed SSOT Projection

| Критерий оценки | Action как физическая таблица в Supabase (`public.actions`) | Action как вычисляемая проекция (`Computed SSOT Projection`) |
|---|---|---|
| **Источник правды (SSOT)** | Размыт: статус дублируется в доменной сущности (`invoice.status = 'paid'`) и строке действия (`action.status = 'done'`). | Строгий: вычисляется напрямую из состояния доменного объекта (`leads`, `lessons`, `invoices`, `tasks`). |
| **Риск задач-призраков (Ghost Tasks)** | **Очень высокий:** При оплате счета через webhook или эквайринг физическая запись действия останется висеть, пока не сработает триггер чистки. | **Нулевой:** Как только инвойс получает статус `paid`, функция проекции моментально перестает генерировать рекомендацию. |
| **Нагрузка на запись (Write Amplification)** | Высокая: каждая смена статуса лида или урока порождает INSERT/UPDATE/DELETE в таблице `actions`. | Нулевая: запись в БД происходит только при реальном создании задачи или фиксации факта активности. |
| **Сложность RLS и безопасность** | Высокая: требуется сложная матрица политик для синхронизации доступа к действиям на чужие лиды/счета. | Нулевая: права определяются RLS политиками базовых доменных объектов. |
| **Время отклика UI («Мой день»)** | Зависит от сетевого раунда к PostgreSQL и скорости JOIN-запросов. | Субмиллисекундное вычисление через мемоизированный хук `useMemo` на клиенте или материализованный кеш. |
| **Масштабируемость** | Деградирует при накоплении миллионов закрытых записей шагов. | Абсолютная: память потребляется только под активное состояние школы. |

**Вердикт:** Физическая таблица `actions` в базе данных признана опасным антипаттерном. Реализация «Action» обязана строиться по принципу **Computed SSOT Projection**.

### 4.3. Инварианты масштабируемости и параллелизма (Anti-Freeze Law & Concurrency Protection)

#### 4.3.1. Защита от зависания интерфейса (Anti-Freeze Law & Temporal Bounding Rule)
Согласно **Правилу 4 контракта разработки (`AGENTS.md`)**:
> *«Запрещены циклические и каскадные invalidateQueries и бесконечные циклы useEffect, подвешивающие UI поток. Все сложные фильтрации, сортировки и расчеты статистики (посещаемость, ближайший урок, суммы) должны быть обернуты в useMemo».*

При росте школы за 2+ года эксплуатации (5 000+ учеников, 20 000+ уроков, 10 000+ платежей и 8 000+ задач) наивная загрузка всех исторических массивов в память браузера для расчета действий в `useCockpitSSOT.ts` приводит к катастрофической деградации:
- Сложность проходов по нефильтрованным массивам достигает $O(N \cdot M)$;
- Синхронное выполнение `aggregateCockpitData` блокирует основной поток JavaScript на **800–2500 мс**, вызывая фатальное зависание интерфейса (UI Thread Freeze).

**Архитектурный инвариант временного ограничения (Temporal Bounding Rule):**
Клиентский движок проекции `CockpitSSOTProjectionEngine` рассчитывает действия **строго в ограниченном операционном окне**:
1. **Уроки и посещаемость:** Выборка строго ограничена диапазоном `selectedDate ± 14 дней` (`WHERE start_time BETWEEN :now - INTERVAL '14 days' AND :now + INTERVAL '14 days'`). Завершенные архивные уроки старше 14 дней в оперативную память браузера для расчета действий **НЕ ЗАГРУЖАЮТСЯ**.
2. **Лиды и долги:** Загружаются только открытые незавершенные сущности:
   - `leads WHERE status NOT IN ('enrolled', 'rejected')`;
   - `invoices WHERE status IN ('pending', 'overdue')`;
   - `tasks WHERE status IN ('open', 'in_progress', 'partially_completed')`.
3. **Бюджет памяти $O(1)$:** Объем выборки на одного оператора гарантированно не превышает **300–500 активных объектов**, что удерживает время расчета в `useMemo` в пределах **3–8 мс** (60 FPS, нулевой риск Freezing).

#### 4.3.2. Защита от параллельных коллизий (Server-Side Action Leases & Soft Locks)
В школах с несколькими администраторами одновременное открытие интерфейса «Мой день» (High-Concurrency Race Condition) порождает риск **двойного контакта (Double Outreach)**:
- В 09:00 администратор 1 и администратор 2 видят одну и ту же карточку: `P1 Новый лид: Екатерина Смирнова (25 мин без контакта)`.
- Поскольку `Action` не является физической строкой в PostgreSQL, стандартный `SELECT ... FOR UPDATE` не применим. Без защиты админ 1 начинает звонить, а админ 2 одновременно отправляет сообщение в WhatsApp.

**Механизм аренды действия (Action Lease / Soft Lock):**
1. При нажатии администратором на любое первичное CTA-действие (`[ Позвонить ]`, `[ Написать в WhatsApp ]`, `[ Выставить счет ]`) клиент запрашивает краткосрочную аренду действия:
   ```sql
   -- Атомарный захват аренды лида в PostgreSQL:
   UPDATE public.leads
   SET active_operator_id = auth.uid(),
       lease_expires_at = NOW() + INTERVAL '5 minutes'
   WHERE id = :lead_id
     AND (lease_expires_at IS NULL OR lease_expires_at < NOW() OR active_operator_id = auth.uid())
   RETURNING active_operator_id, lease_expires_at;
   ```
2. Через Supabase Realtime CDC статус захвата мгновенно транслируется всем подключенным клиентам школы.
3. В интерфейсе второго администратора карточка мгновенно получает состояние блокировки с индикатором: `«В работе у: Елена (до 09:05)»`, а кнопки связи деактивируются.
4. При сохранении результата звонка (Activity) аренда немедленно сбрасывается (`lease_expires_at = NOW()`). При обрыве связи или закрытии вкладки аренда автоматически истекает через 5 минут, исключая вечный deadlock.

### Сценарий 22: Поручение выполнено частично (Partially Completed)

### 6.3. Стратегия ликвидации дублирования: Entity-Keyed Primary Work Unit

#### Кейс «Просроченный счет на 270 €»:
В текущей версии CRM просрочка счета `#20260341` порождает:
1. Запись в `invoices` (`status: 'overdue'`);
2. Параллельный фиктивный платеж со статусом `overdue`;
3. Карточку в блоке 1 «Мой день»;
4. Карточку в `SmartActionHub`;
5. Ручную задачу в `/tasks` («Позвонить по долгу»).

#### Целевое решение:
1. **Канонический URI действия:** Каждое действие в операционном дне индексируется каноническим URI: `urn:school:invoice:20260341`.
2. **Правило слияния (Deduplication Merge):** Если движок приоритетов обнаруживает просроченный счет, он формирует ровно **ОДНУ** первичную карточку `Action`. Если к этому счету привязана ручная задача в `tasks`, она встраивается внутрь карточки счета как подзадача/примечание, а не дублируется отдельной карточкой.
3. **Взаимное атомарное закрытие:**
   - Оплата счета автоматически гасит инвойс, пересчитывает баланс И закрывает связанную задачу в `tasks`.
   - Перенос даты звонка обновляет дату дедлайна инвойса и задачи в единой транзакции.

### 7.2. ADR-005: Decoupled Work Management Architecture (Model B+)

#### Architecture Decision Record: ADR-005
- **Статус:** APPROVED
- **Дата:** 07.10.2026
- **Участники решения:** Principal Architect, Teamwork Preview Orchestrator, Core Team
- **Контекст:** Система управления школой Smart Academy испытывает проблемы с 4-кратным дублированием сущностей на экранах, потерей данных о закрытии задач в `localStorage`, рассинхронизацией Supabase и `localStorage`, а также блокировкой доступа преподавателей к задачам на уровне RLS.

#### Рассмотренные альтернативы:
1. *Модель A (Task-centric):* Попытка свести все действия, звонки и счета к единой таблице `tasks`. Отклонена из-за раздувания таблицы, деградации производительности и невозможности выстроить чистый RLS.
2. *Модель C (4 физические таблицы):* Создание физической таблицы `public.actions` наряду с `tasks`, `activities` и `audit_events`. Отклонена из-за риска «чумы задач-призраков», необходимости сложных каскадных триггеров и рассинхронизации при внешних вебхуках оплат.
3. *Модель B+ (Decoupled Model B+):* Физические таблицы `tasks`, `interactions/activities`, `audit_events` + **вычисляемый движок `Actions` (Computed SSOT Projection)**.

#### Решение:
Утвердить архитектуру **Model B+**:
1. Нормализовать схему `public.tasks` в Supabase, добавив недостающие колонки жизненного цикла (`completed_at`, `completed_by`, `result`, `rescheduled_reason`, `created_by_role`, `created_by_name`, `comments`).
2. Устранить тихий сброс ответственного в `/api/sync/route.ts` и поддержать маппинг строковых имен на `profiles.id`.
3. Открыть доступ преподавателям (`teacher`) к назначенным им задачам в Supabase RLS.
4. Отказаться от физической таблицы `actions`. Реализовать действия на операционном столе «Мой день» как **Computed SSOT Projection** из актуального состояния базовых таблиц.
5. Внедрить **Entity-Keyed Primary Work Unit** для гарантированного устранения дублирования карточек.

#### Последствия (Consequences):
- **Позитивные:**
  - 100% защита данных: результаты закрытия задач и инвойсы сохраняются в PostgreSQL и доступны с любого устройства;
  - Нулевое дублирование: один просроченный счет или лид формирует ровно одну карточку в «Мой день»;
  - Преподаватели полноценно включаются в командную работу через свои учетные записи;
  - Устраняются сетевые сбои `PGRST204` в sync-обработчике.
- **Компромиссы и риски:**
  - Необходимость аккуратной поэтапной миграции метаданных из HTML-комментариев и `localStorage` в новые колонки PostgreSQL без прерывания работы школы;
  - Повышенные требования к оптимизации мемоизации движка `cockpitPriorityEngine.ts`.

### 7.4. Row-Level Security (RLS) политики для public.tasks (Security Hardening)

#### 7.4.1. Эталонный скрипт политик безопасности PostgreSQL
```sql
-- Строго изолированная матрица RLS для public.tasks:
DROP POLICY IF EXISTS "privileged_tasks" ON public.tasks;
DROP POLICY IF EXISTS "tasks_owner_admin_all" ON public.tasks;
DROP POLICY IF EXISTS "tasks_teacher_assigned_select" ON public.tasks;
DROP POLICY IF EXISTS "tasks_teacher_assigned_update" ON public.tasks;

-- 1. Полный доступ для руководства и разработчиков
CREATE POLICY "tasks_owner_admin_all" ON public.tasks
  FOR ALL TO authenticated
  USING (get_my_role() IN ('developer', 'owner', 'admin'))
  WITH CHECK (get_my_role() IN ('developer', 'owner', 'admin'));

-- 2. Преподаватели видят ТОЛЬКО непосредственно назначенные им задачи
CREATE POLICY "tasks_teacher_assigned_select" ON public.tasks
  FOR SELECT TO authenticated
  USING (get_my_role() = 'teacher' AND assigned_to = auth.uid());

-- 3. Преподаватели могут обновлять ТОЛЬКО свои задачи (завершение, отчет)
CREATE POLICY "tasks_teacher_assigned_update" ON public.tasks
  FOR UPDATE TO authenticated
  USING (get_my_role() = 'teacher' AND assigned_to = auth.uid())
  WITH CHECK (get_my_role() = 'teacher' AND assigned_to = auth.uid());
```

#### 7.4.2. Архитектурное обоснование устранения дефектов F-01 (Reviewer 2 Audit):
1. **Ликвидация критической утечки данных (Data Leak Fix):**
   - В первоначальном драфте условие `OR student_id IN (SELECT student_id FROM enrollments e JOIN groups g ON e.group_id = g.id WHERE g.teacher_id = auth.uid())` открывало учителю доступ ко всем задачам по ученикам его групп.
   - Это приводило к утечке конфиденциальной управленческой информации: задач по взысканию финансовой задолженности родителей, служебных поручений директора администраторам о конфликтах, скидках или жалобах на качество преподавания.
   - Новая политика гарантирует: доступ преподавателя **СТРОГО ОГРАНИЧЕН** только задачами с явным назначением (`assigned_to = auth.uid()`).
2. **Устранение битого реляционного предиката (Broken Join Fix):**
   - В схеме базы данных (`initial_schema.sql`): `groups.teacher_id` ссылается на `teachers(id)` (суррогатный UUID первичного ключа таблицы `teachers`), тогда как `auth.uid()` возвращает `profiles.id` (`teachers.user_id`).
   - Сравнение `g.teacher_id = auth.uid()` в PostgreSQL всегда возвращало `FALSE`, создавая скрытый сбой в авторизации. Устранение подзапроса снимает эту проблему.
3. **Ограничение изменения колонок (Column-Level UPDATE Bounds):**
   - На уровне PostgreSQL RLS действует построчно. Чтобы преподаватель не мог через SDK модифицировать системные поля (`title`, `student_id`, `due_date`, `priority`), права на обновление ограничиваются колонками `status`, `result`, `completed_at`, `completed_by` через `GRANT UPDATE (status, result, completed_at, completed_by) ON public.tasks TO authenticated` либо триггер валидации неизменяемости системных реквизитов.

### 8.3. Стратегия отката (Rollback Strategy)
- Все миграции базы данных на фазах 1–6 являются строго **аддитивными** (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`), что гарантирует бесперебойную работу старого кода при откате фронтенда.
